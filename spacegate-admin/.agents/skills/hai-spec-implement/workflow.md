# 执行与 Git 流程

规划文档使用 [templates.md](templates.md)；实现与测试分别复用 [hai-app-create](../hai-app-create/SKILL.md)、[hai-app-tests](../hai-app-tests/SKILL.md)。本文件在执行、续跑或返修任务时读取；文档提交后同步实现先读 [文档差异与基线流程](changes.md)。

## 开始与恢复

1. 检索已有清单、任务编号、需求版本、相关代码和测试。记录用户本次授权的是全部、部分还是指定任务；只规划不创建实现分支或写业务代码。
2. 根据项目规则、现有远端默认分支信息及用户指定，确认实际主分支（集成基线）。记录分支名和起点提交，不把当前功能分支当作主分支，也不固定假设为 main。确实无法确认时只询问该信息，继续可独立进行的文档分析。
3. 检查 `git status`、分支和 worktree。保留无关修改，不自动 stash、reset、清理或提交用户内容；存在未提交改动妨碍切换时使用干净的任务 worktree。任务中的需求文档、清单和源代码须来自同一已确认基线，不能在新 worktree 中悄悄丢掉用户尚未提交的需求。
4. 实施前将本轮目标文档、清单与任务记录落到主分支；规划信息做独立文档提交，不混入无关修改。首次记录完整文档集合及固定目标 SHA，已验收基线保持“未建立”直到整体收尾；文档变更实施保留旧基线并记录本轮 B/S/I 与差异映射。各任务从该主分支开始，后续任务继承前面任务的实际合并结果。没有 Git 的项目在已授权实现范围内初始化，提交目标文档后固定版本；不能使用 Git 或不能写入主分支时记录限制，不能宣称分支交付完成。
5. 恢复已有任务先核对分支、提交与合并记录。若代码已经合并但文档还停在“已验证”，补做合并后的验证/记账；若分支仍有未提交实现，从记录的步骤继续，不再创建相同任务或重写历史。

## 状态与执行前检查

| 清单状态 | 判定依据 |
| --- | --- |
| 待执行 | 范围、验收已明确，尚未开始实现 |
| 进行中 | 正在执行本轮 TDD、门禁或返修 |
| 阻塞 | 需求决策、依赖或环境阻止完成；记录原因与恢复条件 |
| 已验证 | 本轮适用门禁通过，尚未完成主分支集成 |
| 已完成 | 实际合并成功，主分支验证通过且清单/任务记录已提交 |
| 已取消 | 尚未交付的需求被明确撤回/替代，保留原因及关联任务；部分实现已合并时须另行完成清理验收 |

返修将同一任务从“已完成”改回“进行中”，追加新轮次，保留上轮的来源、证据和合并记录。“阻塞”不等于验收通过，环境或既有失败不得标成已完成。清单与任务记录的当前状态必须一致。

选择任务后确认所有前置任务已完成且提交已进入当前主分支，验收仍符合当前需求与实际依赖版本。用户指定了依赖未完成的任务时，列出缺失依赖及可执行入口；用户未授权执行前置任务时，不自行执行它们。

## 任务分支与 TDD

1. 从最新已确认主分支创建独立分支，建议 `codex/<plan>/t001-<slug>`，服从项目已有分支规范。将稳定任务编号、分支和本轮起点 SHA 写入记录；名称不随任务标题变化。进入已有分支前核对它属于该任务，不能抢占同名的其他工作。
2. 先把任务标为“进行中”，写清本轮验收与测试命令。更新已有任务/分支时先合入本轮规划和最新主线，核对工作区文档与固定 S 一致。新项目可先生成/安装最小脚手架，确认测试运行器和已有基线正常，再开始目标行为的 TDD；不先实现业务再补写所谓 Red。
3. **Red**：从公共入口或用户行为添加/调整最小目标用例，覆盖本次规则与必要异常路径；明确需求改变时更新已过时的模板断言并注明需求依据，未改变的回归继续保留。运行并确认因目标行为缺失/缺陷而失败。导入错误、环境未启动或无关回归失败不是有效 Red。若目标用例已经通过，确认已有实现是否满足需求，不能故意破坏代码制造失败。
4. **Green**：复用当前应用及 Hai-Framework 的公开能力，完成使目标用例通过的最小实现，同时同步数据迁移、配置、权限、调用方和说明。配置接入从实际行为验证，不能以文件存在作为可用证据。
5. **Refactor**：在目标测试保护下整理重复和命名，维持仍适用的既有回归通过。行为改变再次走 Red → Green；审查涉及的权限、输入、事务和跨端契约，并修正描述旧模板业务的 AGENTS、skills 与 README。
6. 任务记录保存每轮 Red 的预期/实际失败原因、Green/重构结果、命令、测试或日志位置和实现提交。纯文档/格式任务及完全由现有能力满足的任务记录适用性理由和验证证据，不编造失败或添加措辞镜像测试；有新增/修复行为的任务必须有有效 TDD 证据。

## 验证、提交与合并

门禁结果与 [交接契约](handoff.md) 的被测版本、环境和验收关联。审查发现返回原问题记录；修复后重验受影响项。合并前可用 [hai-pr-review](../hai-pr-review/SKILL.md) 审查固定差异与交付条件，是否创建 PR 仍按用户选择和项目规则处理。

1. 按项目已有脚本和影响范围执行 [分轮验证与集中修复](../hai-app-tests/validation.md)：先收集本轮全部可执行的 typecheck/lint/build/test 及适用 E2E，普通失败不边测边改；汇总后集中修复、再验证。涉及界面保留可核验截图，工作区包优先用 filter；不能拿旧产物/旧截图代替当前行为，未运行、失败、mock 与真实环境分别记录。
2. 把主分支的新提交合入任务分支，解决冲突后重跑受影响门禁；若主分支再次推进，重新同步及验证。冲突按当前需求和双方真实改动解决，不能整体选择 ours/theirs 覆盖其他任务。
3. 通过后将本轮状态更新为“已验证”，只提交本任务的代码、配置、测试、说明和任务信息；检查 staged diff，不能混入用户或其他任务改动。可保留有意义的小步提交，不要求每个任务只有一个 commit。
4. 回到主分支（或它对应的干净 worktree），将任务分支合并；项目没有相反规则时使用 `git merge --no-ff <任务分支>` 保留任务边界。明确授权执行本工作流时可完成本地合并；用户明确只要分支/待审结果时保持“已验证”。遵守项目受保护分支/PR 规则，不绕过；远端推送、PR、发布依用户实际授权处理。
5. 核对实际集成提交及主分支已包含本轮改动；项目采用 squash/rebase 时记录对应提交，不能假定 SHA 保持不变。运行集成后受影响验证。所有任务完成后再按分轮流程收集项目要求的全量门禁和整体需求验收，汇总后集中修复、再验证；最终任务保持“已验证”，直到这些检查通过。不把 Git 合并成功当成业务验证通过。
6. 在主分支将清单和任务记录更新为“已完成”，写入本轮任务分支 tip SHA、实际 merge SHA、集成验证结果和下一步，做独立的文档记账提交。merge SHA 在合并后才能知道，不能预填、也不能 amend 已合并提交去补记录。保留任务分支，以便返修。整个计划/变更轮次的已验收文档与实现基线只按 [基线收尾](changes.md#验收与基线推进) 推进，单个任务完成不代表整体完成。

有中断时保存实际阶段及下一步。已经合并却验证失败时，记录实际 merge SHA 和失败，先收集本轮其余可执行检查，清单保持“进行中”或“阻塞”，汇总后回原任务分支集中修复；后续任务暂不越过失败依赖。收尾报告区分“代码已合并”与“任务已完成”。

## 原任务返修

1. 用稳定编号找到任务清单和原记录，确认属于原验收的缺陷或需求修正；追加“第 N 轮”并关联上次实现/merge SHA、问题来源与受影响需求版本。更新顶部的当前来源、验收与状态，上轮来源与证据保留在历史轮次。新增独立功能另建关联任务，不将持续扩张的范围塞进旧任务。
2. 复用原任务分支，把最新主分支（含上次文档记账）合入后再改代码和任务状态，不从过期分支直接覆盖当前主线。原分支不存在时，核验记录中的 tip/merge 提交后以原名称恢复；记录不足不能猜测恢复点。
3. 先增加能复现问题的回归用例得到有效 Red，再修改代码、配置、需求/任务文档和关联调用方，保留旧轮次记录。业务规则需要新决策时先复审受影响文档，不替用户补定；既有明确修复授权继续有效。
4. 评估依赖该任务的已完成/待执行任务，更新受影响验收与依赖，并运行其必要回归；需要新增实现时形成关联任务或在本次已授权返修范围内处理。
5. 按相同验证、提交、合并和记账流程结束本轮。任务编号、任务文件、原分支保持关联；记录每轮真实提交及验证，不能将旧截图/旧门禁结果当作本轮通过证据。
