# 文档差异与基线流程

用户提交需求/设计文档后要求同步实现时读取本文件；首次实施也按此处记录和收尾基线。任务执行、TDD 与分支合并复用 [workflow.md](workflow.md)，记录结构见 [templates.md](templates.md)。

## 基线含义

在已有任务清单内维护以下信息，不新增状态系统：

| 标识 | 含义 |
| --- | --- |
| B：已验收文档提交 | 当前计划的完整文档集合已被实现并通过整体验收时对应的 Git 完整 SHA；首次未验收时为“未建立” |
| S：本轮目标文档提交 | 本次要实现的文档快照完整 SHA；开始分析时固定，执行期间不随 HEAD 自动变化 |
| I：本轮集成起点 | 规划时确认的主分支完整 SHA，用于定位当前代码和文档状态 |
| H：已验收实现提交 | 最后一次通过整体门禁的主分支完整 SHA，包含实际任务合并；与 B 分开记录 |

B/S 指向文档内容，H 指向经过验证的实现，三者通常不同。记录完整文档路径集合、权威关系和适用范围；多文档用同一 S 快照，不逐份取“最后修改提交”拼接。路径集合包括本轮新增/删除/重命名的旧、新路径；文档拆分、合并时保留来源映射。多个独立计划分别维护基线，不用一个计划的完成替代另一个计划。

## 固定输入与恢复

1. 先读取清单中的 B/H、未完成变更轮次与任务记录，核验 Git 对象和实际代码。旧项目没有 B/H 时，先从历史任务、合并和验收证据追溯；证据不足则标记“未建立”，对当前文档与实现做覆盖核验，形成补齐任务。不能选择 HEAD、最近文档提交或最近 merge 来伪造旧基线；完成覆盖核验及整体验收后才能首次建立。
2. 将用户给出的新提交解析成完整 SHA S；只说“修改了某文档”时，核对该路径的提交历史和当前集成线，默认取分析开始时包含这些已提交修改的 HEAD 快照，说明选择依据。多份文档、跨多个提交时比较 B 到 S 的净变化，不能只看 S 的单个提交。若存在多个无法推断的候选版本，仅澄清目标版本，同时继续独立的影响分析。
3. 用 `git status` 检查文档是否还有未提交修改，包含未跟踪文件。默认实现固定的已提交快照；工作区文档与 S 不同则明确列出，不静默混入、不替用户提交。用户改为采用未提交版本时，先明确新的输入与可追溯记录，不能声称它已由 S 表示。
4. 核验 B/S/H 对象可读取、B/H 的历史验收仍有依据，确认主分支实际包含此前实现。对象缺失先检查本地 refs/浅克隆边界，在允许的仓库访问范围内补齐历史；无法核验时阻塞基线判断，不以空差异表示无变化。H 不在当前集成历史或实现被 revert 时，记录实现漂移并重新核验受影响需求。
5. 常规演进应能证明 B 是 S 的祖先；分叉、回退或历史重写时先记录原因，确认用户目标和端点内容后比较 B/S 两棵树。不擅自改用 merge-base 或三点 diff 缩小变化，不 reset/rebase 用户历史。已存在相同 B/S 的未完成轮次时从其阶段恢复，不重复创建变更和任务。

## 差异与任务映射

1. 先查看仓库级路径变化以发现移出目录的重命名，再比较完整文档集合的内容。以下为命令形状，B/S、路径需替换为核验值，参数按当前 shell 正确引用：

   ```text
   git rev-parse --verify <ref>^{commit}
   git merge-base --is-ancestor <B> <S>
   git diff --name-status --find-renames <B> <S>
   git diff --find-renames <B> <S> -- <全部受管文档的旧路径与新路径>
   git show <B>:<旧路径>
   git show <S>:<新路径>
   ```

   祖先检查退出码 1 表示非祖先，其他错误需单独处理；新增/删除文件只读取存在的一端。重命名检测是线索，结合正文识别拆分/合并，不能只按文件名认定需求新增或删除。富文本文档需读取两端内容/附件，无法可靠提取时记录阻塞，不当作纯格式变化。
2. 用户指出的路径是入口，仍核对计划内全部文档在 B/S 间的变化，以及关联章节、附件和权威关系；跨文档权限、状态、字段、接口和验收一起复审。区分新增、修改、删除、移动/拆分/合并及纯说明变更。读取差异两端上下文和当前代码/测试，使用 [hai-spec-review](../hai-spec-review/SKILL.md) 复审受影响规则；不能把删掉一句话直接解释为删除功能。
3. 在清单追加稳定变更编号（如 C001），保存 B/S/I、文档集合、差异条目、需求位置、关联任务及处理结论。每项变化必须映射到以下结果之一：

   | 情况 | 处理 |
   | --- | --- |
   | 原任务的规则、缺陷或验收变化 | 复用任务编号、文件和分支，更新当前来源与验收；已完成任务追加返修轮次，保留历史证据 |
   | 已有待执行/进行中任务受影响 | 更新其范围、依赖和验收；进行中任务先保存阶段，合入新规划与主线后重新验证，旧测试结果不能证明新验收 |
   | 新的独立可验收能力 | 新建稳定编号并关联变更与依赖；一个任务可处理多项差异，一项跨功能差异可关联多个任务 |
   | 明确移除/替代需求 | 核对调用方、权限、数据迁移/保留与回归；复用原任务或新建有关联的清理任务，不能只删任务记录或擅自删除业务数据 |
   | 原任务尚未交付且已失去需求 | 标为“已取消”并写明来源和替代任务；若有部分实现进入主线，仍需清理/验证任务，不能用取消掩盖残留 |
   | 纯说明/路径调整或当前实现已满足 | 记录语义不变或已有满足的证据、必要验证及来源链接更新，不强造业务任务或 TDD 失败 |
   | 冲突、未决、超出授权范围 | 记录阻塞/排除依据与恢复条件；不能静默忽略，也不能把尚未同步的需求宣称已验收 |

4. 检查受影响任务的上游/下游、共享契约和回归范围，调整依赖顺序并消除循环；不要重开所有历史任务。任务记录关联 C001 与本轮 B/S，清单覆盖映射更新到 S。用户只授权部分差异时可实施独立范围，但同一计划仍有未同步变化就保留 B；需要独立推进时先明确划分计划和文档范围，不能悄悄改成逐文件基线。

## 分支执行与中断

- 将固定的目标文档、差异映射、更新/新增任务记录先集成到实际主分支，再按依赖串行执行。S 在其他分支时先核对范围：只集成本次授权的文档变化，不能顺带合入无关代码；记录来源 S 及实际文档集成提交，并按 Git blob 核对主线文档集合与 S 一致，不强求来源提交 SHA 在 cherry-pick 后保持不变。
- 新任务从最新主线创建分支；原任务复用原分支，先合入最新主线。分支缺失时按记录和当前主线核验后恢复，不从旧代码覆盖主线。每轮按新验收走 TDD、适用门禁、本地合并、集成验证和记账，详见 [执行流程](workflow.md)。
- 发现 S 之后又有文档变化时，保留本轮 S 并列为后续候选；不要在执行中自动改目标或把较新需求当作已完成。若较新文档已进入当前主线并与 S 不一致，暂停依赖该差异的实施及基线推进，保存进度后按用户目标调整本轮。用户明确采用新目标时从未推进的 B 比较新 S，记录目标替换及旧 B/S，核对已合入代码后复用任务和证据，重新映射、复审与验证；不要重复开发已满足项或继续执行被新目标撤回的旧任务。
- 中断时保存目标、任务阶段、实际实现/合并 SHA 和下一步；B/H 保持上次整体验收结果。续跑先核对实际主线与任务分支，再补验证/合并/记账。部分完成、门禁失败、只交付分支或存在未决项时都不能推进 B/H。

## 验收与基线推进

1. 核对本轮每项差异均有处理证据，所有需要实现/清理的任务已实际合并，取消/无需修改项有依据；受影响的原有需求和完整覆盖映射仍成立。首次实施无 B 时对完整文档集合验收。B 等于 S 或 diff 为空时仍检查未完成任务与实现漂移，不能直接宣称完成。
2. 在主分支执行项目要求的整体门禁和需求验收，确认目标文档集合的 Git blob（含删除/新增路径）与 S 一致，工作区没有混入未提交实现。若执行期间主线代码继续推进，检查新提交的影响，对最终主线重新执行必要验证，记录通过验证的完整 SHA H。
3. 只有以上通过后，在主分支独立文档记账提交中将“已验收文档提交”推进为 S，将“已验收实现提交”更新为 H，关闭 C001 并保留旧 B/H、任务合并与门禁证据。H 是记账前已验证的实现提交，不填该记账提交自身的 SHA，不通过 amend/rebase 制造自引用。
4. 提交后核验记录已进入实际主分支，报告 B → S、H、实际合并/记账提交、验证及未完成范围。纯说明变化可以在证据与适用验证齐全后推进文档基线，无需制造代码改动；仍存在未处理需求时报告部分完成并保留旧基线。
