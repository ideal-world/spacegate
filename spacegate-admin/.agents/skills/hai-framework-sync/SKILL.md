# hai-framework-sync — 框架升级与同步

## 能力契约

| 项目 | 契约 |
| --- | --- |
| 能力 | 发现最新发布版本，比较当前到目标的累计差异，处理选择与阻塞，完成应用升级及 skills/AI 入口同步 |
| 适用场景 | “升级 Hai-framework 到最新版本”、指定版本升级、版本差异审查、模板同步或 npm/本地联调漂移排查 |
| 输入 | 当前应用、升级目标及已有约束；当前版本、registry、架构与本地覆盖从项目读取，不要求用户预先提供框架源目录 |
| 输出 | 当前/目标版本及来源、差异与处理清单、迁移后的依赖/代码/配置/skills、验证结果；未完成时给出选择或阻塞及恢复步骤 |
| 限制 | 仅操作授权项目，保留已有改动、架构和私有规则；以实际发布产物为准，未确认选择或未解除阻塞不得越过 |

## 任务入口

- 用户说“升级 Hai-framework 到最新版本”时，直接从当前应用执行下方升级流程。该请求已授权常规依赖更新、必要兼容迁移、skills 合并和本地验证；不为每个文件修改重复确认，也不只输出升级建议后结束。
- 用户仅要求审查/比较版本时，完成现状、目标与差异分析，不安装或修改应用。
- 仅同步通用规范、AI 入口或联调两个仓库时，按需读取 [同步与本地联调](sync.md)；普通应用升级不要求框架仓库可写。
- 先识别当前目录是否为目标应用；确实无法确定目标项目时才询问。应用升级不包含 npm 发布、部署、生产数据迁移或系统级工具安装，已有明确授权时按其范围执行。

## 升级流程

### 1. 确认现状

读取 AGENTS、README、package.json、workspace 配置、lockfile 与相关初始化/调用点，用 `rg` 搜索实现、引用、测试和版本配置。记录 Git 状态及已有改动；工作区有改动本身不构成阻塞，不清空、覆盖或自动 stash 用户工作。

- 识别包管理器、Node/包管理器版本、实际 scripts，以及 SvelteKit、API workspace、fullstack、Vite SPA 或原生端架构。
- 盘点全部 workspace 实际消费的 `@h-ai/*`：记录声明位置、lockfile 解析版本、已安装版本及 npm/local 模式。核对 `catalog`/命名 catalogs、overrides、patchedDependencies、file/link/workspace 映射和联调脚本，不能只看根 package.json。
- 混用多个版本时分别保留基线；未安装依赖时标明已安装版本不可得，以 lockfile 为比较基线，安装后补验。关联代码、配置、环境变量名及 AI 入口，记录已有质量问题；不输出凭据或完整私有配置。

### 2. 发现并固定目标

使用项目有效 registry（包含 scope registry）在线查询；无法访问时诊断网络/镜像/权限，不把缓存或记忆中的版本说成“最新”。

```bash
# 查询示例；PowerShell 使用 npm.cmd / pnpm.cmd。
npm view @h-ai/core dist-tags --json
npm view @h-ai/core@latest version engines dist --json
npm view @h-ai/cli dist-tags --json
```

- 未指定版本/通道时，以 `@h-ai/core` 的 `latest` 为候选；`latest` 即使指向预发布版也应说明并按该通道分析。用户指定版本、稳定版或其他 dist-tag 时遵循其目标；没有满足条件的发布版时提示处理，不擅自替换。
- 对每个已用框架包及用于模板同步的 `@h-ai/cli`，逐一查询候选**精确版本**的存在性、deprecated、engines、dependencies/peerDependencies 和 dist 信息。新增的必要框架依赖同样核验；不能因 core 或 CLI 已发布就假定整组已发布。
- 记录查询时间、registry、每包当前/目标版本与发布产物来源，固定本次目标。发布不齐、镜像滞后、目标被弃用或应用实际采用比候选更晚的发布版时，说明差异并让用户选择等待、指定可用版本/来源或取消相关升级，不静默降级或混装。判断发布先后结合官方发布序列，不能因旧命名 `alpha9` 的 SemVer 排序就认定它更晚。
- 使用精确版本；不能用 `versions` 的字典序、最大 SemVer 或 `pnpm update --latest` 代替 dist-tag 决策。旧命名 `alpha9` 可能在 SemVer 中高于 `alpha.58`，`^`/`~` 范围不保证选中本次目标。

### 3. 比较累计差异并关联应用

在修改依赖前，读取当前到目标版本之间的 Release/CHANGELOG、迁移说明及官方提交差异，覆盖中间版本；混版本逐包比较。上游仓库从包元数据或官方 README 确认，按发布 tag/commit 定位，不能把 main 分支的未发布能力归到目标版本。

没有本地框架源码也应继续：在临时目录用 `npm pack <包名>@<精确版本> --ignore-scripts --pack-destination <临时目录>` 获取当前/目标包，比较 package.json.exports、公开 `.d.ts`、配置 schema/默认值、实现与随包文档；从同版本 CLI 的 `templates/skills/` 获取完整技能目录及入口模板。占位参数先替换为已确认值；只读比较产物，不覆盖应用或执行其中脚本。命令依据：[npm view](https://docs.npmjs.com/cli/commands/npm-view)、[npm pack](https://docs.npmjs.com/cli/commands/npm-pack)。

发布说明不足时以产物、对应源码和测试补充证据；关键兼容差异无法核实时标为待核实/阻塞，不能推断“无破坏性变更”。

逐项检查并关联实际文件/调用点：

- 公开入口、API/类型/错误码、HaiResult 与流/抛错语义、初始化依赖和关闭行为。
- 配置 schema、默认行为、环境覆盖、认证/安全策略、DB schema/迁移、外部服务与引擎要求。
- 构建/运行/发布脚本、第三方 peer 依赖、原生/容器集成，以及版本绑定的补丁是否仍必要。
- skills 及相邻资源、AGENTS/Claude/Copilot/OpenCode 路由；新能力是否可替换本次相关的自定义实现或配置。按 [能力选择规则](../hai-app-create/development.md) 判断适用性，不为升级强行安装无关模块或转换架构。

先给出可追踪的差异清单，再执行迁移：

| 差异/证据 | 应用位置与影响 | 处理类别 | 迁移或选项 | 验收与状态 |
| --- | --- | --- | --- | --- |
| 当前 → 目标及发布/产物位置 | 具体调用、配置、依赖或“不适用”的依据 | 自动处理 / 用户选择 / 阻塞 / 不适用 | 必要修正或带取舍的方案 | 可观察验收、待处理/已解决/待用户 |

### 4. 处理用户选择与阻塞

| 类别 | 处理方式 |
| --- | --- |
| 自动处理 | 目标明确、可保持现有行为的依赖更新、兼容性修正、无冲突的 skills 合并和验证，直接执行 |
| 用户选择 | 存在多个有意义的方案且影响产品行为、架构、成本、Provider 或运维方式，展示证据、选项、推荐与取舍，等待回答 |
| 阻塞 | 无法取得必要产物、依赖不兼容、无法无损合并、必要工具/服务/授权缺失等导致后续无法执行，先处理可自行解决的原因；仍无法推进时说明具体步骤。普通门禁失败先记录，继续独立检查，本轮汇总后集中修复；必要门禁未通过仍不能交付完成 |
| 不适用 | 当前应用未使用且不影响其依赖/运行的变化，记录依据；不要求用户逐项确认 |

- 尽量合并相互独立的选择，明确每个回答控制哪项改动；已给出的目标、授权和选择持续有效，不重复询问。
- 提问时给出问题位置、事实、影响、可选路径及推荐。用户未回答时保持选择待定，可继续独立分析/验证；不能以等待超时替用户选择，也不能先安装一部分框架包造成混版本。
- 阻塞报告包含失败命令、退出码、脱敏关键错误、受影响步骤、已尝试处理、用户最小操作和解除后的验证方式。不要求在聊天中粘贴密钥，不通过关闭检查、忽略 engines 或无依据覆盖依赖掩盖失败。
- 涉及不可逆数据迁移、删除私有覆盖或外部发布时，先准备可审查方案及备份/恢复步骤，再取得该操作所需授权。等待期间不执行依赖该决定的操作；恢复后沿已固定目标和清单继续。

### 5. 执行升级与同步

必要选择和安装阻塞解除后，按既有包管理方式更新所有已用框架包的精确版本，统一修改相关 package.json/catalogs/overrides。保留应用 workspace 协议及无关依赖；必要 peer 更新须来自目标契约，禁止无差别升级全部依赖。

1. 按差异清单迁移调用方、类型、配置、环境变量说明、初始化和构建入口，保留应用行为与架构。新默认行为改变须显式核对；只对生命周期模块遵循 init → use → close，不给 core/serv/纯函数套用生命周期。
2. 用目标版本回归核验已有补丁/本地覆盖：仍必要则针对目标重建并说明依据；只有上游已修复且回归通过时移除。npm 升级遇到本地联调映射时，明确恢复 npm 或继续本地验证的选择，不能只改版本号却继续运行旧源码。
3. 使用当前包管理器安装并更新 lockfile，保留失败诊断；不手改 lockfile 的解析字段。安装后从**各消费 workspace**核对真实版本、公开 exports/类型及框架传递依赖，检查残留旧版/重复解析和本地路径。
4. 按 [同步规则](sync.md) 合并目标 CLI 中适配本架构的完整 skill 目录及 AI 入口。对“旧发布模板、应用现有文件、新发布模板”比较，保留仍适用的私有规则/自定义技能；已明确的业务需求优先于模板默认值，仅未决冲突转为选择。没有旧模板时先辨识私有内容，不直接覆盖。同步版本必须与目标运行时一致。
5. 同步受影响的 README、配置样例、skill 与测试，逐项更新差异清单状态。即使已处于目标版本，也核验解析/配置/skills 漂移；一致时报告无需升级，不制造改动。

### 6. 验证与交付

按应用实际 scripts 和 [分轮验证与集中修复](../hai-app-tests/validation.md) 先收集一轮适用门禁，汇总根因后集中修复、再验证；优先受影响 workspace，跨包契约验证所有消费者。按 [hai-app-tests](../hai-app-tests/SKILL.md) 选择集成/E2E，覆盖启动/关闭、变更 API、认证、持久化等实际路径；CI/发布按 [hai-ci](../hai-ci/SKILL.md) 保留失败阻断。

- 依赖升级后另核对 lockfile 与安装版本、公开入口、配置加载和关键业务流程；build 通过不能替代 typecheck 或运行验收。
- 检查同步后的全部相邻资源、相对引用和各工具入口；目标存在 `check:skills` 时运行，不假定应用具有框架仓库私有脚本。
- 修复本次引入的失败，区分升级前已有失败。必要验收缺服务/凭证/平台时提示阻塞；额外平台或未涉及的真实 Provider 验证明确标为未执行及原因，不能用 mock/Web 结果冒充真实/原生验证。
- 最终报告当前 → 目标及来源、差异处理结果、用户选择、变更文件与同步入口、实际门禁和未验证边界、恢复方法。依赖与必要迁移完成、选择/阻塞已解除且必要验证通过才称“升级完成”；否则报告当前进度与下一步，用户处理后继续完成。
