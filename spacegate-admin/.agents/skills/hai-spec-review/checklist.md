# 需求与设计审查清单

从 [SKILL.md](SKILL.md) 进入。下列各项按项目范围判断适用性，记录文档证据；不将清单中的可选能力或模板默认行为自动转成项目需求。需求与生成代码/规则不同先按入口的“需求基线与模板差异”判定，不以保留模板为审查目标。

## 1. 完备性：业务与边界

- 业务目标、目标用户、要解决的问题、成功标准是否明确；功能能否追溯到目标。
- 核心原则是否能约束冲突决策，如数据归属、历史保留、操作追责、离线策略；避免只写口号。
- 本期范围、排除项、依赖/前提、目标端与部署形态是否明确；不能把“后续支持”当本期实现要求。
- 适用的容量、性能、可用性、安全、隐私、兼容性、可访问性与恢复要求是否可验证，包含负载/测量条件和边界。需要外部服务时明确真实服务、测试替身及失败行为。

## 2. 完备性：功能、角色与数据

- 每项功能有稳定标识、名称、目的、前置条件、参与角色、输入、输出、成功/失败结果和验收条件。
- 角色矩阵覆盖读取、创建、修改、删除、审批、导出等实际操作；明确匿名、自助和管理入口，服务端权限判定及拒绝反馈。
- 操作权限与数据范围分别定义，如本人/组织/指定资源；隐藏按钮不能代替服务端授权。API Key scopes 不能代替租户或资源归属校验。
- 实际存在的管理员、系统账户或其他身份有明确边界；项目涉及多角色/多组织、停用或撤权时有相应规则，不要求采用模板的 admin/user 或管理员自我保护方案。
- 实体、字段、类型、必填/可空、默认值、唯一性、关联、约束、索引需要和数据归属明确。金额/精度/单位、时区、时间格式、文件大小与编码按实际业务定义。
- 稳定 ID 与显示名称区分；状态枚举、合法迁移、历史/版本、软删/恢复、保留/清理、迁移与种子数据有适用规则。敏感字段不能混入公开 DTO、日志或导出。

## 3. 完备性：关键流程与接口

- 关键流程具有触发者、前置状态、步骤、状态变化、责任主体和最终结果；正常路径及实际可能发生的拒绝、取消、超时、失败和恢复均明确。
- 多步骤写入的事务边界、跨服务副作用、通知失败、重试/补偿规则明确；重复提交、并发操作、幂等与部分成功按业务定义，不强制所有操作使用复杂工作流。
- 对审批/发布/导入/上传等实际流程，明确谁在什么状态可执行、重复或冲突请求如何处理、是否可撤回、历史是否保留。
- 接口或共享 contract 定义操作、方法/路径（适用时）、输入输出 schema、验证、错误语义、身份/权限、数据范围与副作用。无需在需求中规定无关的私有函数。
- 列表定义分页、排序、搜索、过滤、空结果及 total 含义；过滤在分页前还是后必须与验收一致。批量操作说明上限、顺序、缺失项与部分失败。
- 文件/流/外部资源明确大小限制、媒体类型、完整性、冲突覆盖、取消与错误传播等选用行为；不能把 S3 ETag 等同 SHA-256，也不能把预签名 URL 等同资源授权。

## 4. 完备性：所有界面与操作交互

对每个适用的页面、菜单、弹窗、抽屉、表单和操作检查以下信息；共用规则可集中定义并引用，无需复制：

| 维度 | 必须能确定的行为 |
| --- | --- |
| 名称与入口 | 稳定标识、显示名称、所在菜单/路由、打开方式、返回去向、适用角色 |
| 展示与输入输出 | 展示字段/顺序/单位、输入类型、必填/默认/可编辑、选项来源、校验、返回/下载内容 |
| 操作 | 按钮/链接名称、执行角色与条件、目标对象、调用接口、状态和数据范围限制 |
| 交互逻辑 | 打开/选择/编辑/提交/确认/取消/关闭的行为；联动、禁用/隐藏条件、批量选择和重复点击 |
| 状态反馈 | 加载、空数据、成功、失败、超时、无权限、处理中；反馈位置、保留输入和重试规则 |
| 导航与恢复 | 分页/筛选/排序后状态、刷新/返回、会话到期、未保存内容处理及列表更新方式 |
| 目标端 | 适用的桌面/移动/原生布局、键盘/焦点/可访问性、i18n；原生能力与浏览器降级规则 |

不接受“提供管理页面”“支持新增修改”“友好提示”“常规交互”等作为完整交互定义。只需规定影响用户行为的约束，视觉细节可由已有设计系统和组件默认行为承担；须明确采用的基线。

## 5. 歧义与一致性

- 主文、附录、原型、接口、数据结构与验收是否对同一事实给出一致结论；冲突引用双方且明确应统一的规则。
- 当前需求与模板 AGENTS、README、skills、代码和测试的差异是否已列为适配项；不能将默认角色、限额、流程或部署形态当成需求文档必须满足的条件。
- “实时”“大文件”“必要时”“适当”“管理员可管理”等描述是否缺少可执行边界；单位、时限、上限、默认值、空值含义是否明确。
- 同一操作在不同入口是否采用相同权限、验证、状态与失败行为；不同流程是否争用或破坏同一数据约束。
- 示例是否符合正文；时间/状态/字段名、角色/权限 code、菜单名、接口名及输入输出是否贯穿一致。
- 待定、可能、未来和备选方案是否有明确决策与范围；不能把两个互斥方案交给 AI 自行择一。

## 6. 技术与 Hai-Framework 正确性

- 选用技术是否适用于当前目标端/部署约束；浏览器没有使用服务端模块、密钥、SQL 或文件系统接口。
- 依赖版本、公开导出、类型、配置和功能开关是否真实存在；核对当前包，不引用未经确认的旧版或未发布能力。新项目可先确定并验证目标版本。框架技术契约以实际版本为准，应用业务行为以需求为准，不因源码仅实现默认业务就否定新需求。
- 生命周期按实际模块契约，reldb/cache 先于 IAM；流、工厂、core/serv/kit 等不臆造 init/close。返回 HaiResult 的业务操作先判断 success，流中错误和框架控制流按其契约处理。
- 使用既有 contract、客户端、认证/通知/存储/审计和组件适用能力；扩展点与缺口有依据，不为业务名新增重复的通用框架，不要求安装无关模块。
- 身份、当前权限、资源范围与副作用分层有可执行规则：IAM 受保护请求验证当前授权，API Key 权限取 scopes 交集，可信 IP 依赖可信对端/代理配置；不能用 userId 重查权限绕过 Key scope。
- 查询、缓存、分页、事务、对象存储/条件写入等设计与所用实现一致；故障不能返回伪造成功或静默扩大权限。
- 验收覆盖业务链及关键边界，有可复现输入/预期输出；区分静态检查、单测、E2E、真实服务与目标设备的证据，不把 mock 当真实集成。

## 7. 命名规范与输出闭合

- 建立术语/标识对照：业务概念、显示名称、实体/字段、接口操作、路由、菜单、按钮、角色/权限 code、枚举。遵守当前项目约定，不引入无关的全仓重命名。
- 同概念同名、不同概念可区分；单复数、大小写、动词、缩写、层级与单位统一。显示文案走 i18n，稳定 code/ID 不随文案改名。
- 操作名表达实际行为和结果，如“禁用”不能同时代表“删除”；状态名、角色名、字段名不能在不同章节复用为不同含义。
- 逐一确认功能/界面操作都能追踪到角色、数据、接口和验收，且设计中无未经需求授权的额外功能。
- 问题修正建议不与其他章节冲突；所有影响行为的选择有决策。最终结论附文档版本、证据范围与剩余问题，不能用“总体可用”掩盖缺项。
