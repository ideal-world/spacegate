# hai-ui-design

## 能力契约

| 项目 | 契约 |
| --- | --- |
| 能力 | 把用户目标转为适配当前 Hai 组件、主题与平台的页面设计 |
| 适用场景 | 新页面、新业务流程、信息结构/布局调整或建立应用视觉约定 |
| 输入 | 用户任务、需求/验收、目标端、当前页面、组件公开类型和已有品牌/设计规则 |
| 输出 | 页面结构、状态与交互、组件映射、必要的全局/页面设计约定和可观察验收 |
| 限制 | 方案请求停在设计；已有实现授权时继续交给 hai-app-create / hai-ui。设计不能补定权限等未决业务规则，组件 API 以实际版本为准。 |

## 设计路径

1. 读取项目入口、需求、实际页面和已有设计，确认目标是新建、局部优化还是整体改版。复用已确认材料；仅澄清会影响用户任务的实质缺口，普通实施细节沿已有授权继续。
2. 确认本页面的主要任务：后台/编辑器重视扫描、操作和状态；官网重视内容表达与行动；文档/帮助重视阅读；作品展示由内容主导。同一个应用的不同页面可有不同任务，不能把营销式大留白强加给高密度操作界面。
3. 按 [页面模式与决策](patterns.md) 选择信息结构：主操作、导航、筛选、内容、详情和反馈。列出初始、加载、空态、错误、成功、无权限及实际需要的长任务/取消/重试状态。
4. 检查安装版本 exports/types 和已有应用实现，按场景 → 组合 → 原子选择 [hai-ui](../hai-ui/SKILL.md) 组件。明确业务负责的数据、鉴权和回调；真实缺口才增加应用组件或提出公共组件改进，不编造 Props。
5. 把设计落到现有 DaisyUI 语义色、Hai tokens、字体层级、间距、密度和布局。保留本次范围适用的品牌、字体和颜色选择；允许业务主题覆盖，组件内不散落新的色值体系。窄抽屉按容器宽度调整，表格滚动由自身承接。
6. 用“角色/操作 → 可观察结果”写验收，包含目标尺寸、语言/主题、长内容、键盘/触摸、减少动态效果和适用失败恢复。实现后交给 [hai-ui-review](../hai-ui-review/SKILL.md) 查看真实渲染与行为，必要时修订设计记录。

## 设计记录

沿用项目已有设计文件。小任务在任务记录或方案中说明即可；跨页面共用规则确实需要持久维护时使用一份 `.agents/instructions/ui-design.md`（或项目既定位置）。记录用户/任务、目标端、主题/token 对应、布局/密度、组件、交互和验收；页面仅记录差异，避免复制需求或整份组件 API。

前端工作与 SDD 通过 [交接契约](../hai-spec-implement/handoff.md) 传递范围和验收。设计来源可参考 [UI/UX Pro Max](https://github.com/nextlevelbuilder/ui-ux-pro-max-skill) 的场景匹配与全局/页面分层，以及 [Impeccable](https://github.com/pbakaus/impeccable) 的任务模式；所有建议须经现有产品、平台和真实组件核验。
