# 分轮验证与集中修复

适用于开发、审查修复、升级后的质量门禁与整体验收。默认执行“收集一轮 → 归并问题 → 集中修复 → 定向回归通过 → 较完整验收”，不要遇到一个普通失败就修改代码并从头重跑。新增行为的目标用例仍可做小范围 TDD Red → Green；它不要求提前运行整套门禁。

## 1. 确定本轮检查

- 先读当前 `package.json`、任务依赖与环境要求，按影响范围列出命令、工作目录、前置条件和预期证据。优先 workspace filter；用户要求全量验收时保留全量范围。纯文案/文档修改只做适用检查，不新增镜像测试。
- 一轮默认按 typecheck → lint → build（涉及构建/配置/模板/跨包契约）→ test → 相关 E2E 调度；顺序服从真实依赖。同轮收集不等于同时运行：只有输出目录、端口、数据库、容器与 fixture 均隔离的检查才可并行，共用 `dist`、`.svelte-kit` 或预览产物的构建与测试必须串行。
- 使用现有任务编排或一个临时调度脚本逐项执行、捕获真实退出码并保存日志。不要用跨检查的 `&&`、全局 fail-fast 或 `|| true` 代替结果收集；脚本内部有前置短路时，确认后续检查是否真正执行，必要时分别调度等价子任务，保留原门禁的最终验收。

## 2. 收集全部可执行结果

- 本轮开始后保持被测源码、配置、依赖和运行环境稳定；协作 agent 也不得边测边改，不运行自动修复。普通类型错误、lint 错误、测试断言失败只记录，继续其余具备前置条件的检查。
- 只有真实前置失败才阻塞依赖它的检查，例如依赖无法安装、执行器无法启动、上游构建未产生必要产物、必需服务不可用。标明阻塞原因，继续独立检查；确实无法继续收集时才提前结束本轮、集中修复阻塞。不得使用旧构建、旧镜像或旧截图让下游假通过。
- 为每轮使用独立且被 Git 忽略的日志目录，例如 `tmp/validation/round-01/`。逐项记录命令/范围、源码版本及未提交改动、环境、状态（通过/失败/阻塞/未执行）、退出码、耗时和日志路径；未执行与不适用须说明原因，不能写成通过。超时、取消和环境失败单列，不能当作断言失败或忽略。
- 调度脚本等子进程退出后再记录结果；重定向或管道不能覆盖实际退出码。所有必需项均有有效通过结果，整轮才算通过；收集到任何失败或阻塞时，汇总必须保留非成功状态。
- 完整输出写日志，AI 先读汇总及每类失败的有限上下文，再按需定位原始日志；不反复载入整份成功日志、密集轮询或启动尚未结束的同一检查。长任务期间定期简述进度。

## 3. 集中分析与修复

- 本轮可执行检查结束后，把问题按根因去重，记录位置、证据、影响、修复项及关联门禁。上游故障造成的连锁失败合并处理；区分本次引入、原有问题和环境问题。
- 在已有授权范围内集中修复本次范围的问题，保留仍有效的断言与回归。不能靠删断言、跳过用例、放宽超时或关闭规则换绿灯。环境故障先保存证据、确认恢复条件，再定向重试；不反复重跑到偶然通过。
- 下载超时先区分 registry、DNS、代理等网络前提与实际编译/业务错误。复用包管理器的有界重试、可信镜像和缓存，保留总时限与每次结果；只对可安全重复的瞬时网络操作重试，不重试断言或掩盖业务失败。超时/取消后确认本轮进程树及已登记资源回收，再重试或启动冲突任务。
- 新发现的独立问题加入同一清单；修复期间的小范围诊断不触发从头全量重跑，也不能替代下一轮必要验收。

## 4. 先定向回归，再扩大验收

- 集中修复后，先用最小适用范围验证原失败、已解除的阻塞及直接受影响的消费者；保留必要构建/服务前置。定向回归仍失败时继续归并和修复，只重跑失败及受新改动影响的项，暂不启动较完整门禁。
- 相关问题均已验证解决后，再按影响扩大到工作区或完整用户流程验收；影响范围不明、共享配置/依赖改变或用户要求全量时，执行全量门禁。扩大验收发现新问题时，仍回到“收集 → 集中修复 → 定向回归通过 → 扩大验收”，不要每改一处就重复整套流程。
- 只有源码、依赖、配置、工具、环境及所用产物等输入均未改变的已通过项才可复用，并注明来源轮次或缓存；输入变化使相关结果失效。最终所有必需检查必须对最终代码仍有效，缺项不能称为完成。真实部署、Provider、浏览器或原生验收不能只引用静态检查/构建缓存。
- 保留原有 CI/发布门禁的失败阻断；问题收集时继续运行不代表允许失败提交发布或忽略 required checks。
- 每轮都在 finally/teardown 停止本轮进程、清理本轮临时工程/容器/镜像/数据；确认退出和资源释放后再运行冲突任务。日志、截图与报告保留到问题分析和交付结束，再按项目约定清理，不覆盖失败证据、不提交验收产物、不删除用户资源。
- 部署夹具先检查固定公开基础镜像，仅确认缺失才拉取；成功 create 先登记完整 ID，再在私有 PID namespace 内异步准备 APT/pip/sshd。所有准备 exec 转交同一取消信号，等待本地客户端 close 后按该 ID 停止全树并核验消失。总准备 deadline 早于 hook 并预留回收预算；公共缓存不删，私有 tag 回收前复核内容 ID/owner。未取得可信 create 回执或测试进程被强制终止时记录未知，不能按名称或 label 认领资源。
- 浏览器执行器默认将每轮、每组的证据分别放入忽略的 `test-results/run-*/group-*`；只清理本轮临时数据库/上传数据。显式 `HAI_AUTH_EVIDENCE_DIR`、`--output` 和 Playwright HTML 输出目录会保留，取消也不删除已有报告。不要复制私有环境、密钥或业务数据库到证据目录。
- 经托管 `test:e2e` 入口为服务子进程提供绝对 `HAI_E2E_DATA_ROOT` 和显式测试后端，隔离继承的 `HAI_*` / `PUBLIC_*` / `VITE_*` 与用户 `.env.local`。仅本轮测试启用 `HAI_E2E=1`；普通开发与生产的 dotenv 加载、共享后端守卫不放宽。启用 transport 的验收使用本轮可信 ring 和 registry，不能关闭加密掩盖客户端契约问题。
- 最终报告各项门禁状态、执行/复用范围、修复结果和未验证原因；mock、容器、真实服务及原生结果分别说明。只陈述实际证据，不以“脚本执行完了”代表验证通过。

公开 API 变更需验证 package.exports 实际入口与配套声明，核对根/子路径真实导入和浏览器打包；不使用 src/dist 深层导入绕过缺失公开产物。Svelte 默认组件、明确 selective/type-only 导出与 client/server 分隔按实际契约验收，不把内部 Provider/Deps 扩成公共 API。
